# Operations

How to run, watch and troubleshoot the services. Grows as phases add components.

## Services (docker compose)

| Service | What it does | Health check | If it's down |
|---|---|---|---|
| `db` | PostgreSQL 16 + pgvector | `pg_isready` | API returns 503 on `/health/ready`; nothing works |
| `redis` | Login/sign-up rate limiting | `redis-cli ping` | **API keeps working**: rate limiting fails open and logs a warning. `/health/ready` shows Redis as `error` but stays `ok` overall |
| `backend` | FastAPI API; runs migrations on start | `GET /api/v1/health/live` | UI can't load data |
| `worker` | Processes uploaded documents | Heartbeat file younger than 60 s (`python -m app.worker --healthcheck`) | Uploads still succeed and stay **Queued**; they're processed as soon as a worker is back |
| `frontend` | nginx serving the React app, proxying `/api` | container running | UI unavailable |

## The ingestion worker

```bash
docker compose logs -f worker          # JSON logs: "job done" with chunk count and duration
docker compose up -d --scale worker=3  # more throughput; workers never take the same job
```

Job states (`ingestion_jobs.status`): `queued` → `running` → `done`, or back to `queued` (retryable error, exponential backoff), `failed`, or `superseded` (a newer version was uploaded first).

| Setting | Default | Meaning |
|---|---|---|
| `NEXUS_JOB_MAX_ATTEMPTS` | 3 | Attempts before a job is marked failed |
| `NEXUS_JOB_RETRY_BASE_SECONDS` | 5 | Backoff: 5 s, 10 s, 20 s… |
| `NEXUS_JOB_LOCK_TIMEOUT_SECONDS` | 300 | A job "running" longer than this (worker crashed) is reclaimed by another worker |
| `NEXUS_WORKER_POLL_SECONDS` | 1 | Idle polling interval |

The worker stops gracefully on `SIGTERM` (`docker compose stop`): it finishes the current job first.

### Useful queries

```sql
-- Queue overview
SELECT status, count(*) FROM ingestion_jobs GROUP BY status;

-- Recent failures with the internal error (users only see a safe message)
SELECT document_id, attempts, last_error, finished_at
FROM ingestion_jobs WHERE status = 'failed' ORDER BY finished_at DESC LIMIT 20;

-- Jobs that look stuck
SELECT id, worker_id, locked_at FROM ingestion_jobs
WHERE status = 'running' AND locked_at < now() - interval '5 minutes';
```

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Documents stay **Queued** | Worker not running | `docker compose ps worker`, `docker compose logs worker` |
| Document **Failed**: "No text could be extracted" | Scanned PDF (image only) | OCR isn't supported yet; upload a text-based PDF |
| Document **Failed**: "Embedding failed" | Provider down, out of retries, or bad API key | Check `last_error` (query above), fix, then click **Reprocess** |
| Chat always answers "I couldn't find this" | Offline mode only answers questions worded close to the documents, or the documents aren't **Ready** | Rephrase with the documents' words, check **Documents**, or switch to `NEXUS_ANSWER_PROVIDER=openai` |
| Chat returns **503** "AI service temporarily unavailable" | LLM provider timeout, 429 or outage | Retry; check the provider status and the API logs |
| Chat returns **502** | LLM provider rejected the request (often a bad API key or model name) | Check `NEXUS_OPENAI_API_KEY` and `NEXUS_CHAT_MODEL` |
| Search quality dropped after changing `NEXUS_EMBEDDING_PROVIDER` | Old chunks were embedded by the previous model | **Reprocess** each document |
| Login returns **429** | Too many attempts (per IP per minute, or failed logins per account per 15 min) | Wait for `Retry-After` seconds |
| Upload returns **413** from nginx | File over 25 MB | Limit is `NEXUS_MAX_UPLOAD_MB` (20) at the API; nginx allows slightly more so the API's clearer message is shown |

## Data

- Uploaded files live in the `uploads` Docker volume (`/data/uploads`), shared by `backend` and `worker`. Keys are generated by the server (`org/<org>/doc/<doc>/v<n>/original.<ext>`); user file names are never used as paths.
- `docker compose down -v` deletes the database **and** uploaded files.
- Backups (production): PostgreSQL dump plus a copy of the uploads volume, taken together. Object storage (S3) replaces the volume in the AWS design (Phase 10).
